# S31 BLE feasibility: existing sources and binary ABI

Read-only audit, September15. Status: **NOT IMPLEMENTED / TARGET NOT RUN**. Only this report was written; no build, download, UART, reset or firmware operations. Longrun864 was not touched. BLE remains a board-product category gap, not an excluded fixture item. Scope is the18 BLE titles retained in `category-peripheral-audit.md`, especially original on/off, advertising intervals and scan modes.

## Concrete conclusion

The local pinned S31 controller binaries match the project's RV32 little-endian **single-float ABI**, so an incompatible float ABI is not the immediate obstacle. However, the S31 controller uses a different OS interface and lifecycle from the existing C3 NuttX adapter. Its archive supplies **weak assertion stubs for51 OSAL functions**, making a superficially successful link particularly misleading. A real NuttX OSAL and S31 PHY/controller bringup are required before the already-present original `bttool`/Zblue path can work. This is substantial new controller work; it is not a config-only addition and cannot responsibly be promised complete before the September17 peripheral session.

The smallest useful path is **BLE-only, awake controller, main-XTAL clock, initially Wi-Fi disabled, in-process VHCI exposed as `/dev/ttyHCI0` to the existing openvela Bluetooth service/Zblue/bttool**. This establishes original enable/state/disable, one legacy advertiser and scanning first. Multiple advertising sets, privacy/address modes, pairing and Wi-Fi coexistence remain separate original acceptance gaps; a basic advertiser does not close all18.

## Binary and missing-callback evidence

Existing toolchain `riscv32-esp-elf` esp15.2.0_20251204 was used only for `readelf`, `nm` and `objdump` inspection. Both S31 archives under `IDF/components/bt/controller/lib_esp32s31/esp32s31-bt-lib/` report ELF32 little-endian RISC-V, flags0x3 RVC/single-float ABI for all members examined:37 members in `libbtdm_common.a`,119 in `libble_app.a`. Current build883 uses `-march=rv32imafc_zicsr_zifencei -mabi=ilp32f`. The archives have no reported `Tag_RISCV_arch`; therefore header compatibility is established, not a proof that every instruction/link relocation/runtime path works. No firmware link was attempted.

A symbol-set union of the two archives leaves59 undefined symbols; adding existing `IDF/components/esp_phy/lib/esp32s31/libbtbb.a` reduces this to30, mostly libc/compiler runtime, PHY and legacy BTDM data-boundary symbols. This is an archive-level superset before garbage collection, not the final link's unresolved count. Crucially, absence from the undefined list does not mean OS adaptation exists: `libbtdm_common.a` already defines weak `wr_btdm_osal_*`. Disassembly of `wr_btdm_osal_task_create` calls `wr_btdm_assert` then returns-1. Strong real NuttX definitions must replace the reachable weak hooks; inspect symbol binding in the final ELF rather than merely accepting linker success.

The exact missing OSAL groups from the pinned header/archive are:

- Event queues: `wr_btdm_osal_eventq_{init,deinit,get,put,put_to_front,remove,is_empty}`; events: `wr_btdm_osal_event_{init,deinit,reset,run,is_queued,get_arg,set_arg}`. Preserve queued-event deduplication and remove semantics; task queues alone are not interchangeable.
- Mutex: `wr_btdm_osal_mutex_{init,deinit,pend,release}`; semaphore: `wr_btdm_osal_sem_{init,deinit,pend,release,get_count}`; callout: `wr_btdm_osal_callout_{init,deinit,reset,mem_reset,stop,is_active,get_ticks,remaining_ticks,set_arg}`. Pinned FreeRTOS port uses ESP timer callouts and millisecond OSAL ticks; do not confuse these with NuttX scheduler ticks.
- Task/IRQ: `wr_btdm_osal_task_{create,delete}`, `wr_btdm_osal_intr_{alloc,free}`, `wr_btdm_osal_hw_{enter_critical,exit_critical,is_in_critical}`. The reference allocates level3/IRAM controller IRQs on the pinned core. S31 CLIC priority and SMP critical nesting must be implemented, not forwarded to FreeRTOS macros.
- Time/memory/identity: `wr_btdm_osal_time_get`, `time_ms_to_ticks`, `time_ticks_to_ms`, their32-bit variants, `get_time_forever`, `malloc/free`, `ets_delay_us`, `read_efuse_mac`, `srand/rand`; optional mmgmt block routines and `btdm_osal_elem_mempool_init/deinit` according to configuration. Internal-memory allocation must really remain internal, not select PSRAM.

The BLE extension table is separately defined in `porting_btdm/controller/ble/src/ble.c`: version/magic plus `_malloc`, `_free`, `_osi_assert`, `_os_random`, `_ecc_gen_key_pair`, `_ecc_gen_dh_key`, `_esp_reset_rpa_moudle`, `_ecc_aes_cmac`. Initialization registers it with `esp_register_ext_funcs` and calls `esp_ble_register_bb_funcs`. Existing xTS ECC/AES work does not automatically satisfy the Bluetooth wrappers' byte ordering or signatures. Pairing requires these actual crypto contracts.

Additional concrete dependencies are `btdm_lp.c` clock/reset/`esp_phy_enable(PHY_MODEM_BT)` and disable, `btdm_coex.c`'s16 weak coexistence wrappers, `btdm_log.c`/assert handling, `ble.c`/`ble_msys.c` buffers, and the standard VHCI source. `btdm_external.c` itself only wraps BT baseband power tables; it is not an OS adapter.

Completion criterion for this coding step is a linked image with reachable OSAL hooks strong and no fake success stubs, followed later by actual controller init/HCI reset evidence. It is not itself original xTS PASS.
2. **Expose standard VHCI through NuttX H4 and enable the existing original service/tools.** Add `nuttx/arch/risc-v/src/esp32s31/esp32s31_ble.c` implementing `bt_driver_s` open/send/close and callback delivery, modeled on C3 `esp_ble.c` but using S31 `esp_vhci_host_register_callback` and real send backpressure. Register `uart_bth4_register("/dev/ttyHCI0",...)`; integrate a guarded call in board `src/esp32s31_bringup.c` and enable the existing framework service/LE Zblue/tools in the isolated BLE profile. Reuse existing `frameworks/connectivity/bluetooth/service/stacks/zephyr/hci_h4.c` and `tools/{bt_tools,adv,scan}.c`, not a new command clone. First physical acceptance then uses original `bttool` enable/state/disable/state, `adv start -i32/160/1600/16384 -n vela-adv-test -m legacy`, and original scan modes with the phone counterpart. C3's empty close and dropped-send-on-not-ready behavior must not be copied blindly into an on/off acceptance path.

## Practical risks and deadline boundary

S31 controller work may compete with the internal SRAM already needed by Wi-Fi, IRQ stacks and kernel heaps; archive size is not a valid runtime allocation estimate. Standard VHCI allocates/copies temporary buffers and frees them after callbacks, so callbacks must consume/copy before returning. ISR/critical paths and their data need internal memory and correct IRAM placement; a successful FLAT bringup would not establish SMP/MMU correctness. The IDF memory-release APIs in S31 `bt.c` still log TODO and return success, so do not promise reclaimed controller memory on disable.

The existing main-XTAL and PHY clock work can be reused as references, but starting/stopping Bluetooth must not turn off Wi-Fi's shared PHY. Disabling coexistence for the initial BLE-only experiment is legitimate staging; it provides **no evidence** for the two original BLE/Wi-Fi coexistence cases. Those still require actual simultaneous BLE traffic and the published Wi-Fi cycles. Multiple-address/set advertising and scanner PHY limits must come from real HCI feature responses and phone observations. Keep original unsupported/unknown requirements visible, including the document's unresolved2M scanning note.

Given September19 submission and reserved physical testing from September17, these are feasible next implementation boundaries, not a completion guarantee for all18 BLE cases. A missing OSAL/controller is a software blocker; buying a phone or NRF fixture alone will not solve it. Current contribution adds **zero PASS**.
