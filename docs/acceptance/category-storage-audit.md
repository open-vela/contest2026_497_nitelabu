# Category xTS storage, KVDB, OTA and NetApp audit

Audit date: 2026-09-15. Read-only audit; no UART, reset, flashing, build, credential access, or source changes. Published source: `openvela-dev/docs/zh-cn/test_dev_guide/openvela_xts_test_cases.md`, section two. This file does not change acceptance criteria or execute document commands.

There are **37 published headings** in this audit: filesystem25, KVDB2, OTA5, NetApp5. **No exact target PASS is established by this audit.** The25/35 common count excludes these headings. Filesystem4.1.1 is a document mismatch whose actual steps are iperf networking; the network audit may establish evidence and should own its final status. Do not infer all37 are mandatory for this board, and do not invent N/A without an applicability decision.

Source availability is substantially better than current test firmware coverage. `tests/testcases/vela_fs_test/CMakeLists.txt` already wires original stress/stability/power-off commands. Current810 and883 configs have FS_TEST=y solely for FS_TEST_EDONLY/md5; FUNCTION, STRESS, STABILITY, POWEROFF are all off. KVDB, curl CLI, SSH and FTPD are off. Original components exist locally (external/framework repositories are ignored by ordinary rg traversal; direct paths or --no-ignore are necessary); no download is needed.

Existing supporting evidence: `backups/2026-09-09-runtime/README.md` records LittleFS write/read/reboot persistence/delete; `checkpoint771-xts.md` and `logs/xts767-fstest.log` record10 original RAM fstest loops. `xts736-footprint.md` identifies writable7MiB LittleFS /apps at0x500000..0xbfffff and read-only application filesystem. These do not satisfy the distinct category workloads below. Searches across backup logs for the named category commands found build-list mentions, not execution results. Existing HTTP demo/YMODEM success is supporting network/transport functionality, not curl/scp/ftpd/OTA acceptance.

## Minimal offline preparation and September19 schedule

1. **First priority: original filesystem and KVDB commands.** Prepare one isolated category profile using the existing source/CMake wiring; preserve current864 firmware and all flash ranges. FS common documented options include TESTS_TESTCASES, FS_TEST, FUNCTION/STRESS/STABILITY/POWEROFF, ARCH_SETJMP_H, PSEUDOFS_SOFTLINKS and8192 stack (32768 for test04). Keep source assertions/counts unchanged. Choose filesystem types explicitly: TMPFS for RAM-only support, persistent dedicated LittleFS for reset/power cases, FAT for fatutf8, ROMFS for romfs. A profile being buildable is not PASS.
2. **Prepare safe scratch storage before running destructive category workloads.** Candidate865 registers only raw1MiB MTD and has not run; needs planned filesystem/block mapping for dd, FAT and persistent suites. Reuse the existing double-read/all-FF backup guard before any scratch mutation. Do not run fill/max-name/format/power-loss workloads on production /apps or AppFS. Do not pretend1MiB scratch meets the unadjusted20MiB fragmentation example: published permits resource-based values, document them.
3. **KVDB can reuse existing frameworks/system/utils implementation.** Choose DIRECT or SERVER deliberately, enable an existing persistent backend, define isolated persist path and mount mapping; preserve temporary-storage coverage in cmocka. UNQLITE matches published persist.db semantics most closely; its source is locally present. FS_TEST_FUNCTION currently has no explicit CMake block, so enabling it alone does not create missing functionality; the specific commands above are under stress/stability/power-off.
